Collection Description
RESTful services for credential verification via the Atlas API ecosystem. ## Overview ## A Certifying Organization is the official administer (either web site, data repository, or flat file), whether a governmental entity for public protection purposes or professional association, of licenses and certifications to individuals or organizations that require the demonstration of a certain level of knowledge or ability. Contact us at atlassupport@symplr.com to get setup with an API Key on our API Sandbox. Below is a summary overview of the API. <b>A detailed API Workflow document is available at <a href='DataWorkFlows.pdf'>DETAILED API DOCUMENTATION</a></b> <b>A detailed API Discover License document is available at <a href='discoverLicenseDocs.pdf'>DETAILED DISCOVER LICENSE DOCUMENTATION</a></b> ## Process ## The VerifyNOW API provides for a verification to be submitted to a Certifying Organizations and the results of the verification provided via a Webhook. When a verification is sent using verificationSubmit the parameters are evaluated to ensure they are correct. certOrgFields POST; { api_key : 'client api key' , CertOrgID : '776AD35B-4141-43E6-A550-F9078B7307B5' } certOrgFields RESULT; { Name: 'LicenseNumber', hasOptions: false, options: Count = 0 } verificationSubmit POST; { ClientRequestID: 'client unique id', FirstName: 'Alison', LastName: 'Alter', CompanyName: '', Email: '', CertOrgID: '776AD35B-4141-43E6-A550-F9078B7307B5', api_key: 'client api key', InputList: [ { FieldName: 'LicenseNumber', FieldValue: '831269' } ] } verificationSubmit RESULT; { ClientRequestID: 'client unique id', RequestID: 176887, Responsemsg: '' } If they are the API immediately return the requestID created in our system and the verification is submitted to the processing engine. Depending on load and the specific Certifying Org’s web site, the requestID will be processed anywhere form 10 seconds to 2 minutes. After the verification is processed by our engine, any webhook that has been using addWebHook is called with the results of the engine process. ## CertOrg Discovery ## The <discoverLicense> endpoints are designed to provide a search capability for those certification organizations that provide a full data listing of licenses. This allows for smoothing the On Boarding process by determining a license number and certification organization prior to submitting an actual real time verification. Use discoverLicenseData to determine what licenses are available to search for a State. Use the Keyword filter to search for specific certifications like Nurse or Physician. Use discoverLicense to search for a license based on existing data you have in order to verify if the license number exists or to find a license number based on partial information. Use discoverLicenseText to do a search for a license based on a single text input string, like you might use in a “type ahead” style user interface. There are other ‘discovery’ end points which allow the determination of the specific Certifying Org for a license verification. If, for example, the Certifying Org for New York Physicians is needed, there a several endpoints which provide for the retrieval of filters and allow for the determination of which Certifying Org and input fields are needed for a specific verification. These endpoints can be used to create client UIs that allow for the determination of the correct Certifying Org. There are two ways to go about discovery of Certifying Orgs. By Keywords or By State. You can view the keywords by calling certOrgKeywords. For the keywords to be used, let’s say “New York” (33) and “Physician” (633), package those up to certOrgbyKeywords and it will return the provider(s) for those keywords. You can view the available States by calling certOrgStates. For the State to be used, send the State_ID to certOrgsbyState and it will return the provider(s) for that State. Once the desired Certification Org is established, pass the certOrgID to certOrgFields to get the required input fields for that provider. ## 3rd Parties ## Verifications requires a dependency on 3rd party resources which are outside the control of Atlas. Therefore, processing times can significantly vary based on the 3rd party infrastructure. ## WebHooks Notes ## A verification is considered processed if we receive a 200 status back from the client WebHook endpoint. Items are automatically marked as unprocessed two ways: 1. For all new verification requests. 2. For subsequent requests of the same verification, where the status changes, i.e. going from unverified to verified or vice versa. Each hook url has its own processed flag, so if 'url A' returns 200, it will be marked as processed, but if 'url B' returns 500, it will remain unprocessed. All unprocessed items are periodically automatically retried. The web hooks work by distinguishing when their is a change in a verification. That change doesn't matter whether it is a standard 30 day retry, or a manual retry. If the verification changes status, such as goes from Active to Expired, then the webhook is triggered. If a verification is re-verified, a webhook will only be called if there is a change in status for the verification. To send all webhooks in the sandbox, request that the SendAll flag be set. “apiKey” that is submitted during the addWebHook is the key that will be returned to the webhook in the header as “apiKey”. ## Verification Status Descriptions ## Postive values are additive, meaning a status of 9 would be Active and Excluded. VERIFICATION PROCESSED 1 Active. This item is considered valid by the issuing provider, or for an Exclusion is Not Excluded. 2 Expired. This item is considered expired by the issuing provider, or for an Exclusion is Excluded or has a potential Exclusions. 4 Revoked. This item was valid at one time, but has been revoked by the issuing provider. 8 Exclusion. This item is an Exclusion verification. 16 Invalid. The issuing provider was not able to find this item by the data provided
